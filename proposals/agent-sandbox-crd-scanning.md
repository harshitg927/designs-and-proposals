# Proposal: Posture scanning for agent-runtime CRDs (Agent Sandbox / Agent Substrate)

## Summary

Extend the Kubescape Rego posture engine to treat the emerging agent-runtime
custom resources as first-class scan targets. Concretely: add a control
framework covering Agent Substrate's `WorkerPool` and `ActorTemplate` and Agent
Sandbox's sandbox resources, and wire the same controls into admission so a
non-hardened agent definition never gets scheduled. No new sensing, no eBPF
work. This rides entirely on capability Kubescape already has.

## Motivation

Google made GKE Agent Sandbox GA and introduced Agent Substrate in May 2026.
Both concede that the Kubernetes control plane was not built for how agents
behave, and both push the security-relevant configuration into new object types
that live outside the workloads Kubescape scans today. An `ActorTemplate` decides
whether model-generated code runs under gVisor or a shared kernel. A `WorkerPool`
decides whether one runaway actor can starve every other session multiplexed
onto it. These are posture decisions, and right now nothing treats them as such.

The workload here is untrusted by definition. The code an agent runs is
generated by a model at runtime, so the isolation and egress posture of the
resource that defines it is the whole ballgame. A misconfigured `ActorTemplate`
is a misconfigured trust boundary.

This is the cheap, near-term move that plants the flag before anyone else has
bothered, and it seeds the CRD schema knowledge and Substrate control-plane
touchpoints that later runtime-attribution and enforcement work will need.

## Goals

- A named control framework ("Agent Runtime Hardening") scanning the agent CRDs.
- Findings surfaced through the existing CLI, operator, and MCP-server paths.
- Admission-control variants (VAP or Kubescape admission) that reject or warn on
  non-hardened agent definitions.
- Framework mapping to OWASP LLM and MITRE ATLAS where the control maps cleanly.

## Non-goals

- No runtime sensing changes. This proposal does not touch the node-agent, and
  does not attempt to see inside gVisor or Kata. That visibility gap is real and
  is addressed separately.
- No per-session or per-actor runtime attribution. Out of scope here.
- No claim of behavioral enforcement. This is static posture and admission only.

## Proposal

Add controls against the agent-runtime resources. Initial candidate set:

- **Runtime isolation is enforced.** The actor is pinned to a gVisor or Kata
  runtime class, not a default container runtime that shares the host kernel.
- **Default-deny egress is set.** The actor's network posture denies egress by
  default, with an explicit allowlist, rather than open egress.
- **Resource ceilings exist.** CPU and memory limits are set so a single actor
  cannot exhaust a shared worker pool. Relevant precisely because Substrate
  multiplexes many actors onto few pre-warmed Pods.
- **Image provenance is trusted.** The actor image resolves to an allowlisted
  registry, and where available is signature-verified.
- **Credentials are scoped per session.** Service-account tokens and secrets are
  not broadly mounted into the actor. Least privilege on the session identity.
- **Snapshot storage is protected.** Where idle sessions are snapshotted to
  storage, the target is encrypted and access-scoped, since a snapshot is
  volatile memory and filesystem state at rest.

Controls are written in Rego against the CRD schemas, consistent with the
existing regolibrary. Each carries remediation text in the Kubescape style.

## Admission

Paired with admission control, a non-hardened `ActorTemplate` never runs in the
first place. This turns the scan from a report into a guardrail and gives the
same signal at author time (IDE, CI) and at deploy time (admission), which is the
left-to-right story Kubescape already tells for standard workloads.

## Enumeration gap

Most agents are not API-server objects. They live in Substrate's side control
plane. Static CRD scanning covers the definitions (`WorkerPool`,
`ActorTemplate`), which is the correct and sufficient scope for this proposal.
Enumerating live actors from the Substrate registry is a dependency for later
runtime work and is explicitly deferred.

## Alternatives considered

- **Do nothing and wait for the runtime work.** Rejected. The posture controls
  ship in a quarter, are useful immediately, and do not block on the harder
  eBPF-visibility problem landing first.
- **Generic "AI security" checks bolted onto existing frameworks.** Rejected.
  The agent CRDs have specific, checkable fields. Vague checks help no one and
  do not survive review.

## Open questions

- Target repo and format: governance PR (design doc) versus tracked issue.
- Which agent-runtime CRD schemas to pin against first, and their version
  stability given Substrate is explicitly an early project.
- Whether to ship the framework as a standalone or fold it under the CADR work.
